# Архитектура и данные

## Сборка

`scripts/build.py` читает данные и JPEG, встраивает фотографии как data URI и вставляет каталог/JS в `src/template.html`. Получается один автономный `index.html`. Сборщик также встраивает `src/bin-panel.html`, `src/bin-builder.js` и `data/bin-schema.json`. Сборка детерминирована; дата/случайные числа в HTML не добавляются. Python 3.10+, без pip/npm.

`src/app.js` ожидает глобальные `PHOTOS` (создаёт сборщик) и `DATA` (JSON из `<script id="data">`). Не дублируй `const PHOTOS` в app.js. Функция `validate()` проверяет импортированный план по текущему каталогу и доступным точкам.

## Четыре разных идентификатора/координатных пространства

| Значение | Пример | Что означает |
|---|---|---|
| Метка | A54 | Условное название размещения в этом проекте |
| `guid` | GUID размещённого объекта | Идентичность конкретного объекта |
| `x/y` фото | 0.4 / 0.7 | Положение значка, X направо, Y вниз |
| `world` | X −149.76, Y 79.9152, Z 175.04 | Координаты мира, Y — высота |
| SpawnID | −1, экспериментальный 10054 | Параметр движка; НЕ метка A54 |

`gameSpawnId` в экспорте сайта остаётся `null`: сайт не устанавливает рабочие игровые идентификаторы. Формула 10000+номер применялась в экспериментальном моде, а не доказана как штатное правило.

## Фото

`data/photo-layout.json` — четыре зоны с `id/name/width/height/asset/points`. `points` содержат `id/x/y/guid/world`. Всего 40 активных точек: Egypt 11, Center 15, Rome 4, China 10. `data/placements.json` дополнительно содержит 15 точек исключённого Volcano и 5 EpicSpawns.

Только `x/y` меняются при исправлении разметки. Пользователь специально попросил не отражать фотографии. Эталон их JPEG-байтов хранится в `reference/map-assets.json`; размеры — в метаданных.

Файлы `reference/original-site/` — исторический срез перед текущей правкой. Там прежняя, заведомо неверная для части точек разметка. Это источник сравнения, не рекомендуемая версия для публикации. Текущая схема — v3.

## Каталог и план

`data/catalog.json`: 147 групп. В записях сохранены `guid`, `node`, номер волны, `comps`, подгруппы `subs`, параметры и отображаемые имена. Некоторые названия являются справочными соответствиями, а не выгрузкой локализации игры. Сохраняй пояснения `nameNote`.

План содержит:

- `format: gw2-timepark-plan`, `version: 1`, `name`;
- `waves["1".."10"]`: `groupGuid`, `compositionGuid` (GUID или `auto`), `assignments` (GUID подгруппы → A-метка или `auto`), `ambush`;
- при экспорте: `createdAt`, `readyForFrosty: false`, `damageChanges: false`, `placementMap`, `excludedLocations`, `photos`, `resolvedWaves`.

План назначает подгруппу на метку, не на экранные пиксели. После исправления разметки старый план сохраняет ту же метку/GUID — не ожидаемое пользователем старое место на картинке. Автоматической миграции нет. Валидация может заменить неизвестные/исключённые точки на `auto`; это нужно явно сообщать пользователю.

`localStorage` ключ: `gw2-timepark-select-v1`; не меняй его без плана миграции. Доступность хранения и origin для `file://` зависят от браузера. JSON — переносимая резервная копия. Импорт показывает подтверждение замены; исключения обрабатываются статусом на странице.

## Публикация

Root `index.html` работает на GitHub Pages при публикации из ветки. Workflow сначала проверяет актуальность сборки и тесты, затем строит `_site/index.html`; на Pages отправляется только `_site/`. Он не выполняет игровые инструменты и не публикует reference/local выгрузки как часть сайта. Приватные файлы всё равно нельзя коммитить в сам репозиторий.

## Экспериментальная запись BIN

Описание алгоритма и границ поддержки — `BIN-BUILDER.md`. Генератор не отправляет пользовательские BIN по сети и не кладёт их в localStorage. Все записи применяются к новым буферам; загруженный оригинал не перезаписывается. Корректность записанных полей не считается подтверждением применения движком.
